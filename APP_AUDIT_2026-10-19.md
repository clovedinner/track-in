# Trakio application audit

Date: 19 October 2026

## Verdict

Trakio has a working product foundation and can support controlled, operator-assisted testing. It is not ready for a general self-service paid launch. The main blockers affect attribution correctness, saved integration settings, outbound delivery recovery, customer billing, and isolation of authenticated money-site integrations. Cosmetic work alone will not close these gaps.

There is no defensible percentage-complete estimate: the screens exist, but several failure paths and commercial workflows remain incomplete. Readiness should be measured against the release gates at the end of this report.

This audit does not change application behavior or database records. The existing homepage CTA edit remains separate. Database checks used read-only metadata/aggregate queries; no migrations, payments, registrations, clicks, or conversions were submitted to the configured database during the audit.

## What was examined and verified

- Next.js routes, public tracking endpoints, generated page scripts, conversion intake, provider adapters, worker/repository code, account/session code, billing code, Prisma schema and migrations, dashboard queries, forms, navigation, deployment workflow, runbook, and test suites.
- The configured database's migration history, selected indexes, aggregate delivery state, expired-active subscription count, and campaign ownership relationships. This verifies the database configured in this workspace, not every installation or production host.
- Headless Chrome smoke checks of the local homepage and signup. Screenshots were inspected at 375px and 1440px. The pricing link, signup page, password visibility, and unauthenticated admin redirect were exercised.
- Authenticated administration UI was reviewed from source and supplied screenshots. No customer session was impersonated. Full authenticated browser flows, real payment settlement, live provider acceptance, geographic network coverage, restore rehearsal, and load capacity were not certified.

## What is already worth keeping

- A single deployable Next.js application with an explicit PostgreSQL schema and migration history.
- Cryptographically random public click IDs, parameter allowlisting, and database-backed visit records.
- Conversion creation and outbound-job creation happen in one transaction.
- Database uniqueness protects conversion/event replay and duplicate outbox destinations.
- Most private routes explicitly scope customer data by account ownership. Campaign creation checks that the selected offer and source belong to the account.
- Passwords use salted scrypt; production session cookies are HTTP-only, secure, and SameSite=Lax.
- Delivery retries distinguish transient and permanent HTTP failures, with an audited manual retry operation.
- Custom conversion management has basic validation, ownership checks, reference checks, and audit entries.
- Timezone is persisted per account. Security headers and deployment/runbook foundations exist.

Preserve these foundations while repairing the gaps below.

## Priority definitions

- **P0:** blocks a general paid launch because it can lose/misattribute conversions, damage saved integrations, break payment activation, or create a serious multi-customer security exposure.
- **P1:** complete before promising unattended production operation. These affect reliability, account access, reporting trust, or release safety.
- **P2:** usability, consistency, maintainability, and support improvements. Some should accompany the related P0/P1 fix.

## Confirmed release blockers

### A01 · P0 · Propeller delivery ignores the configured external-ID parameter

The UI can configure `visitor_id=${SUBID}`, and click capture saves the result under `visitor_id`. The Propeller adapter only searches `subid`, `SUBID`, `clickid`, `CLICKID`, `click_id`, and `CLICK_ID`. It never reads the configured `externalId.parameter`. TrafficJunky's adapter has a similar fixed-name limitation; TrafficStars already supports its configured parameter.

**Evidence:** A local call with `{ visitor_id: '1135905635428167681' }` throws `PropellerAds requires the original click token (SUBID/clickid).` The configured database also contains one permanently failed Propeller delivery with that error. This explains a real outbound failure independently of timezone; it does not establish why an earlier RDP visit was missing.

**Improve:** Resolve the original platform ID through the saved external-ID mapping consistently across adapters. Validate it at setup/test time and test the exact advertised parameter names.

Sources: [Propeller adapter](/D:/Track.in/src/lib/providers/propeller-ads.ts:51), [provider dispatch](/D:/Track.in/src/lib/outbox/provider-delivery.ts:36).

Follow-up, 19 October: the workspace adapter now resolves the configured external-ID parameter, with legacy aliases retained for unmapped sources. Adapter/outbox regression tests pass. A read-only dry run of the actual failed record constructed the correct `visitor_id` request using a stub transport. Production deployment and real delivery retry remain outstanding; no provider request or database write was made by that verification.

### A02 · P0 · Editing a traffic source can overwrite its postback credentials

The traffic-source list sanitizes URL credentials to `[redacted]`, passes that representation into the table, and opens the editing form using the selected table row. The form then submits the masked URL as the replacement configuration. A user can edit only a source name and unintentionally replace its real postback key. Duplication from the same table has the same problem. The dedicated edit route uses raw configuration, so the two entry points behave differently.

**Evidence:** Passing a key-bearing URL through `safeTrafficSourceConfiguration` and then the save parser produces a valid saved URL whose `key` is literally `[redacted]`.

**Improve:** Separate display data from editable configuration. Preserve unchanged secret values on the server; never accept masking placeholders as credentials. Test name-only edits, per-event edits, and duplication.

Sources: [list serialization](/D:/Track.in/src/app/admin/traffic-sources/page.tsx:26), [table edit modal](/D:/Track.in/src/app/admin/traffic-sources/traffic-sources-table.tsx:67), [form initialization](/D:/Track.in/src/app/admin/traffic-sources/traffic-source-form.tsx:50), [save payload](/D:/Track.in/src/app/admin/traffic-sources/traffic-source-form.tsx:128).

### A03 · P0 · Direct tracking can silently reuse attribution or stop on storage errors

The generated page script checks a URL `cid` or a domain-wide local-storage value before considering the new campaign context. A fresh ad landing with a new `cpid` and a new platform ID can therefore reuse an old campaign's `cid` and never call `/g/click`. Browser storage access is also unguarded. If accessing or writing local storage throws, script execution stops. Setting `directLoaderStarted` before the failing operation prevents straightforward reruns on that page.

**Evidence:** Executing the generated script with a new campaign and old stored CID produced `cid: old-campaign-cid` and no `/g/click` request. A second execution with denied storage threw `storage denied`. The separate `/g/.js` loader also accesses storage without recovery.

**Improve:** Define a new ad arrival separately from journey continuation. A new campaign landing must not inherit a previous visit just because local storage exists. Handle blocked storage, avoid retaining stale attribution after failed capture, and make the CID-ready/error state observable. Test reloads, navigation, repeated ad clicks, cross-campaign visits, storage denied, and multiple tags.

Sources: [generated tracking script](/D:/Track.in/src/lib/setup/campaign-tracking-script.ts:37), [secondary loader](/D:/Track.in/src/app/g/[asset]/route.ts:3).

### A04 · P0 · Claimed delivery jobs have no crash recovery

The worker marks up to 25 jobs as `processing` before delivering them sequentially. Claim queries only select `pending` or `retryable_failed`; there is no expired-lease recovery. Killing/restarting the process mid-batch can leave the remaining jobs permanently in `processing`. Manual retry only accepts failed statuses, so the customer cannot repair those rows through the UI. Provider fetches also lack an explicit application timeout.

**Improve:** Add bounded request deadlines, expiring leases with safe reclaim and worker fencing, and recovery tests that terminate a worker after claiming a batch. Preserve idempotency when an upstream accepted a request before the local worker lost its response.

Sources: [claim and completion repository](/D:/Track.in/src/lib/outbox/prisma-repository.ts:13), [sequential worker](/D:/Track.in/src/lib/outbox/worker.ts:101), [retry eligibility](/D:/Track.in/src/lib/admin/delivery-health.ts:44).

### A05 · P0 · Checkout is still an invoice/payment prototype

The UI displays a hardcoded wallet address and a hand-authored QR pattern labelled `Dynamic QR`. That pattern is not generated from the invoice or wallet. `I have sent payment` only calls `setSubmitted(true)` in the browser; it neither records a payment claim nor initiates verification. The API creates a database invoice, but no implemented payment-provider adapter or TRON monitor reconciles a transfer to that invoice. `checkoutUrl` is returned but not used. The page itself still calls the flow a mockup.

**Improve:** Choose and integrate a real payment-verification path. Invoice terms, expiry, payment destination, correct QR, amount/network/asset verification, transaction confirmation, webhook handling, persisted status, and account activation must form one tested workflow. If using a shared wallet, establish a reliable invoice-to-transfer matching mechanism; equal plan amounts alone are ambiguous.

Sources: [wallet and QR](/D:/Track.in/src/app/admin/subscribe/subscribe-page.tsx:45), [mockup description](/D:/Track.in/src/app/admin/subscribe/subscribe-page.tsx:148), [submission button](/D:/Track.in/src/app/admin/subscribe/subscribe-page.tsx:221), [billing service](/D:/Track.in/src/lib/billing/service.ts:36).

### A06 · P0 · Authenticated conversion intake still assumes one money site

The S2S endpoint uses one environment-wide bearer secret and the constant source `primary_money_site`. Duplicate lookup is global on `(source,event_id)` and occurs before resolving the supplied click. Two customers sending the same ordinary order/event ID can collide: the second receives the first conversion's duplicate result instead of a new conversion. There is no per-account money-site identity or per-site credential lifecycle.

**Improve:** Scope authenticated integrations, credentials, event identities, and ownership checks to the account/money site. Keep the intentionally public browser-compatible endpoint as a separate contract. Add two-account tests using identical event IDs and attempted cross-account attribution.

Sources: [shared source constant](/D:/Track.in/src/lib/conversions/intake.ts:3), [duplicate lookup](/D:/Track.in/src/app/api/conversions/route.ts:57), [environment secret](/D:/Track.in/src/lib/config/environment.ts:31).

### A07 · P0 · Customer-configured postback URLs expose server-side request risk

Postback URL validation only checks URL syntax and HTTP/HTTPS. A paying customer's configuration can point the server worker at loopback, private services, link-local addresses, or an external redirect into those destinations. Delivery uses normal fetch behavior without an outbound destination policy. This was established by code inspection; no internal-network requests were attempted.

**Improve:** Enforce an outbound destination/egress policy for custom endpoints, including DNS resolution, redirects, private IP ranges, URL credentials, and timeouts. For the three supported platform adapters, use their expected platform endpoints unless an explicitly supported custom endpoint needs broader access.

Sources: [URL validation](/D:/Track.in/src/lib/providers/config.ts:106), [outbound dispatch](/D:/Track.in/src/lib/outbox/provider-delivery.ts:66).

### A08 · P0 · Subscription expiry is not enforced by the access check

`requireCurrentUser` only checks `users.account_status`. It does not evaluate subscription status or `current_period_end`, and no expiry/reconciliation job was found. An account can remain active after its dated plan expires unless an external webhook or an operator updates it. Conversely, changing only the subscription row may not grant the intended account access.

**Improve:** Define a single entitlement calculation with lifetime/manual exceptions, paid-through time, renewal, grace, and cancellation policy. Reconcile denormalized account state. Decide separately how expired accounts affect dashboard access, ongoing paid ad traffic, conversion intake, and delivery.

Source: [current-user/access guard](/D:/Track.in/src/lib/auth/current-user.ts:13).

## Reliability, data correctness, and security work

### A09 · P1 · Billing needs a defined state machine and reconciliation

The generic signed webhook is a useful foundation, but transitions are too permissive for charging customers:

- A different confirmation event ID can reconfirm the same invoice without a guarded payment-state transition.
- Transaction hashes/provider transaction IDs are indexed, not unique where reuse must be prohibited.
- An old cancellation/expiry event locates the latest subscription for the provider, potentially suspending a newer subscription.
- A refund changes payment status without a corresponding entitlement policy.
- Webhook `plan` can override the invoice's saved plan; amount and currency matching are optional.
- Date parsing does not ensure period end is after start or that the chosen period is appropriate.
- Early renewal starts from `now` by default and can discard prepaid time; a fixed 30-day period and the UI's `Monthly` wording need one explicit policy.

**Improve:** Bind events to invoice/payment/subscription identities, validate legal transitions, handle duplicate/out-of-order events, reconcile provider state, define renewal arithmetic, and test concurrent events. Clearly document application billing units versus blockchain asset precision.

Sources: [webhook business logic](/D:/Track.in/src/lib/billing/service.ts:89), [webhook handler](/D:/Track.in/src/app/api/billing/webhook/route.ts:7), [billing constraints](/D:/Track.in/prisma/schema.prisma:77).

### A10 · P1 · No application rate limiting was found on public write/authentication paths

Sign-in, signup, public click creation, and `/postback` can repeatedly consume hashing, database, and delivery resources. The public postback contract explicitly requires bounded abuse protection. Clear account-not-found messages were deliberately requested by the owner; retain that product decision while protecting the route against high-volume probing and password attempts.

**Improve:** Add appropriate shared/deployment-level rate controls, request bounds, observability, and tests. Set limits differently for legitimate ad bursts, login attempts, signup, and public conversions.

Sources: [sign-in](/D:/Track.in/src/app/api/auth/signin/route.ts:7), [signup](/D:/Track.in/src/app/api/auth/signup/route.ts:7), [public intake](/D:/Track.in/src/app/postback/route.ts:29), [direct visit endpoint](/D:/Track.in/src/app/g/click/route.ts:37).

### A11 · P1 · Accepted request IDs can violate the database UUID column type

The correlation-ID helper accepts arbitrary strings such as `rdp-test` or `request_123`. Tracking and conversion records store correlation IDs in UUID columns. A valid-looking incoming `x-request-id` from a client/proxy can therefore make an otherwise valid write fail. IP headers are similarly passed directly into PostgreSQL INET without normalization or a documented trusted proxy chain.

**Improve:** Always generate/validate the internal UUID, preserve an external trace ID in a compatible separate field if needed, and normalize trusted client-IP headers. Test common proxy request IDs and IPv4/IPv6 formats.

Sources: [request ID acceptance](/D:/Track.in/src/lib/observability/correlation-id.ts:3), [direct write](/D:/Track.in/src/app/g/click/route.ts:71), [schema types](/D:/Track.in/prisma/schema.prisma:267).

### A12 · P1 · Applied migration history and the repository do not fully agree

The configured database's completed billing-foundation migration has a different SHA-256 checksum from the current file. The ownership migration has three historical rolled-back attempts and a completed final attempt; those earlier failures are historical, not currently unresolved. SQL also enforces case-insensitive traffic-source name uniqueness using `lower(name)`, while Prisma declares ordinary `(ownerId,name)` uniqueness.

**Improve:** Recover and document the exact applied migration history, reconcile discrepancies without resetting customer data, and use new forward migrations for future changes. Align schema declarations, expression indexes, naming, and introspection expectations. Rehearse a clean installation and upgrade from a realistic older database.

Sources: configured database `_prisma_migrations`/`pg_indexes`, [billing migration](/D:/Track.in/prisma/migrations/20261015000000_billing_foundation/migration.sql), [ownership migration](/D:/Track.in/prisma/migrations/20261014000000_scope_data_to_users/migration.sql).

### A13 · P1 · Configuration does not consistently control runtime behavior

Direct URLs use configured external/custom parameter mappings, while redirect URL generation relies on provider defaults and only adds the cost field. The UI presents many outbound token chips such as `{var1}`, `{campaign.name}`, and `{event.type}`, but the adapters fill a small hardcoded set of provider fields; no general expansion of those advertised chips was found. Offer URL chips similarly imply substitution beyond the actual canonical `cid` append/overwrite. Provider identity is inferred from a few macro spellings, so an equivalent macro may be rejected or routed to another adapter.

**Improve:** Define one explicit incoming/outgoing token contract and renderer. Generate both tracking modes from the same saved mapping. Offer only supported token chips, reject unresolved attribution placeholders before outbound delivery, and avoid depending on ambiguous macro spelling to identify a platform.

Sources: [redirect/direct generation](/D:/Track.in/src/lib/setup/campaign-setup.ts:73), [macro inference](/D:/Track.in/src/lib/providers/identity.ts:4), [offered token chips](/D:/Track.in/src/app/admin/traffic-sources/traffic-source-form.tsx:11), [offer chips](/D:/Track.in/src/app/admin/offers/offers-client.tsx:10), [destination construction](/D:/Track.in/src/lib/tracking/click.ts:64).

### A14 · P1 · Account timezone is not applied consistently to reporting boundaries

Dashboard and conversion filters use `parseDateInTimezone`, but campaign detail constructs midnight UTC boundaries directly. Its `To` date is exclusive midnight at the start of the selected date, unlike the inclusive-day behavior elsewhere. Daily grouping uses UTC dates. The dashboard still displays `UTC` and `All dates use UTC` even when its filter uses the account timezone.

**Evidence:** The timezone helper itself also mishandles some DST transitions: requesting `2026-10-04` in `Australia/Sydney` produced `2026-10-03T13:00:00Z`, which formats locally as 3 October, 11 PM, not 4 October midnight.

**Improve:** Share one tested day-boundary implementation with inclusive date-range semantics, including DST transitions and invalid calendar dates. Keep UTC storage and delivery scheduling. Display/report grouping should reflect the selected account zone.

Sources: [campaign filters](/D:/Track.in/src/lib/admin/campaign-views.ts:159), [timezone parser](/D:/Track.in/src/lib/timezone.ts:20), [UTC labels](/D:/Track.in/src/app/admin/dashboard/page.tsx:98), [daily grouping](/D:/Track.in/src/lib/metrics/queries.ts:96).

### A15 · P1 · Custom conversion switches do not mean what the reporting UI implies

`includeInConversions` controls whether an event gets a dynamic column, while total conversion counters still count all conversion rows. `includeInRevenue` and `includeInCost` are stored and shown but do not affect aggregate calculations. `sendPostbackToTrafficSource` is consulted for per-event routing, while single-URL routing sends without consulting those definitions.

**Improve:** Define separate semantics for showing a column, counting a primary conversion, revenue/cost inclusion, and postback eligibility. Apply them in a shared metrics/routing layer, and make the UI wording match those semantics.

Sources: [custom metrics](/D:/Track.in/src/lib/admin/custom-conversion-metrics.ts:15), [overview aggregation](/D:/Track.in/src/lib/metrics/queries.ts:69), [postback routing](/D:/Track.in/src/lib/conversions/intake.ts:159).

### A16 · P1 · Custom events are not connected through the full setup journey

Custom event values can be up to 80 characters and contain values that public intake rejects under its 64-character restricted format. Setup snippets still only generate registration/FTD tags. Repeated events such as deposits require a unique `txid`; without one, later same-type events for a visit are deliberately deduplicated. Setup does not make the recurring-event requirement sufficiently concrete.

**Improve:** Use a shared event-value schema and generate tracking instructions from the account's event definitions. Show the exact intake `et` value, transaction-ID requirement, example, and copyable URL for each event. Test first deposit and two distinct later deposits as well as replay of one transaction.

Sources: [custom value validation](/D:/Track.in/src/lib/admin/custom-conversions.ts:30), [public event identity](/D:/Track.in/src/lib/conversions/intake.ts:112), [default GTM events](/D:/Track.in/src/lib/setup/gtm-snippets.ts:45).

### A17 · P1 · Financial representation is inconsistent

Provider adapters do not share one currency-unit policy: Propeller treats IDR as zero-decimal and most others, including JPY, as two-decimal; TrafficStars and TrafficJunky use different zero-decimal lists. Overview/campaign revenue sums do not group by currency. Conversion detail displays raw `valueMinor` as if it were a display amount: `100 USD` rather than converting a value of 100 minor units into the major-unit display.

**Improve:** Centralize the supported currency/unit contract and formatting, keep integer storage, group monetary aggregates by currency or explicitly convert them, and verify exact provider payload amounts. Do not enable profit/ROI promises until costs are persisted and reconciled; the current cost module is only an unused input parser.

Sources: [Propeller formatting](/D:/Track.in/src/lib/providers/propeller-ads.ts:71), [TrafficStars formatting](/D:/Track.in/src/lib/providers/trafficstars.ts:43), [TrafficJunky formatting](/D:/Track.in/src/lib/providers/trafficjunky.ts:60), [conversion details](/D:/Track.in/src/app/admin/conversions/conversions-client.tsx:23), [cost parser](/D:/Track.in/src/lib/costs/import.ts:112).

### A18 · P1 · Existing test/deployment gates do not protect a paid release

The unit suite fails in the navigation expectation and the Phase 1 flow mock, which lacks the newer `customConversion.findMany` call. These failures do not independently prove the production endpoint always fails, but they leave the central contract test red. Browser tests still expect Basic Auth/old text and skip without explicit environment variables. No focused billing tests or executable direct-loader behavior tests were found. The deployment workflow does not run lint, unit, integration, or browser tests before deploying.

**Improve:** Restore the suite and make the release pipeline fail when core verification is skipped. Add targeted coverage for the actual regressions in A01-A17, two-account access, billing transitions, worker recovery, and both browser/S2S conversion flows. Run database tests only against a verified disposable database.

Sources: [flow test](/D:/Track.in/src/app/phase1-flow.test.ts:121), [navigation test](/D:/Track.in/src/lib/admin/navigation.test.ts:14), [browser suite](/D:/Track.in/tests/e2e/admin.spec.ts:10), [deployment workflow](/D:/Track.in/.github/workflows/deploy.yml:21).

### A19 · P1 · Deployment can disrupt the active release and declare weak health as success

Deployment resets the active checkout, installs dependencies with `npm install`, migrates/builds in the serving directory, and restarts processes. There is no isolated release directory or automated rollback. It appends a resolved database IPv4 address to `/etc/hosts` on every deploy, bypassing normal DNS changes and implying root-level deployment permissions. Verification checks process presence plus liveness; readiness only validates environment variables and never queries PostgreSQL or verifies the worker heartbeat. Build success does not prove runtime DB schema compatibility.

**Improve:** Build/test a pinned release before switching traffic, use reproducible dependency installation, make migration compatibility explicit, provide rollback, remove persistent DNS pinning, and verify database/schema and worker health after release. Use a dedicated service account. Rehearse this on staging.

Sources: [deployment script](/D:/Track.in/.github/workflows/deploy.yml:49), [readiness endpoint](/D:/Track.in/src/app/api/readiness/route.ts:10).

### A20 · P1 · Secrets and personal data need a completed storage/retention design

Credential-bearing postback URLs are stored directly in JSON configuration and copied into outbox destinations. `credentialSecretRef` exists but the worker does not resolve it through a secret store. Raw IP, user agent, referrer, and attribution tokens are retained with no implemented retention/anonymization job. Runbook guidance exists, but no completed backup/restore rehearsal evidence was found in the repository. This is an evidence gap, not proof that the host/provider has no backups.

**Improve:** Separate/encrypt integration secrets, minimize sensitive stored URLs, define operational retention periods, and implement scheduled cleanup/anonymization. Rehearse recovery and record the measured restore result. Add an account-data deletion path compatible with immutable tracking records and foreign keys.

Sources: [traffic-source and click models](/D:/Track.in/prisma/schema.prisma:182), [worker configuration loading](/D:/Track.in/src/lib/outbox/prisma-repository.ts:41), [operations runbook](/D:/Track.in/OPERATIONS_RUNBOOK.md:53).

### A21 · P1 · Main reporting queries will grow with every tracked visit

Campaign listing loads all related clicks and conversions into application memory to count them. Offers do the same. Traffic-source listing executes several queries per source and loads all conversion event types for counting. Campaign detail also loads all date-range rows for a daily series that is no longer rendered. These shapes can work with test data while becoming slow and memory-heavy under paid traffic.

**Improve:** Count/group in PostgreSQL, paginate lists, eliminate unused queries, and measure query time/memory with representative account volumes before promising capacity. Existing indexes are a useful start; add indexes based on measured query plans, not hypothetical scale.

Sources: [campaign list](/D:/Track.in/src/lib/admin/campaign-views.ts:122), [offers API](/D:/Track.in/src/app/api/admin/offers/route.ts:17), [source queries](/D:/Track.in/src/app/admin/traffic-sources/page.tsx:18), [detail loading](/D:/Track.in/src/lib/admin/campaign-views.ts:189).

### A22 · P1 · Test traffic and event-based rates can mislead customers

Setup-test visits/conversions are excluded from real postback delivery but are included in visit and conversion totals. Dashboard recent activity ignores active date/campaign/source/event filters, so its rows can contradict the visible totals. The numerator is all accepted events, not unique converted visits; registration plus FTD on one visit can yield a rate above 100%.

**Improve:** Mark test traffic consistently and exclude it by default, filter activity using the same snapshot, and define whether the main conversion-rate metric counts primary conversions, unique converted visits, or events per visit. Document the selected formula in the UI.

Sources: [setup-test records](/D:/Track.in/src/app/api/admin/campaigns/[campaignId]/setup-test/route.ts:24), [unfiltered activity snapshot](/D:/Track.in/src/lib/admin/verification.ts:3), [rate formula](/D:/Track.in/src/lib/metrics/formulas.ts:37).

### A23 · P1 · Paid plans are marketing labels without enforced entitlements

Starter, Operator, and Expanded have prices and descriptions, but no central plan-capacity definitions or creation/usage enforcement were found. All active accounts pass the same guard. Terms such as `more campaigns` and `more source connections` do not give customers measurable limits.

**Improve:** Define the exact commercial difference between plans, store it centrally, enforce relevant limits atomically, show usage, and specify upgrade/downgrade behavior. Alternatively sell one real plan until meaningful differences exist.

Sources: [plan definitions](/D:/Track.in/src/lib/billing/service.ts:5), [account guard](/D:/Track.in/src/lib/auth/current-user.ts:13), [campaign creation](/D:/Track.in/src/app/api/admin/campaigns/route.ts:50).

## UI, workflow, and maintainability findings

### A24 · P2 · Campaign Edit is largely a view-only drawer

The campaign table's `Edit` action opens summary details, not fields to update the campaign name, offer, source, or mode. The API only supports active/paused status updates. `Open setup` links in this drawer and after campaign creation still navigate to a dedicated setup page, while the detail page has the requested setup modal.

**Improve:** Implement a real, validated editing workflow, or label the action `Inspect`. Use the same setup component/modal behavior across all entry points and protect changes that would rewrite historical attribution.

Sources: [campaign drawer](/D:/Track.in/src/app/admin/campaigns/campaigns-table.tsx:95), [status-only API](/D:/Track.in/src/app/api/admin/campaigns/[campaignId]/route.ts:12), [creation success flow](/D:/Track.in/src/app/admin/campaigns/new/campaign-form.tsx:91).

### A25 · P2 · Source edits lose state; displayed health is not a real check

The source form always submits `enabled: true`, regenerates a reduced configuration, and does not preserve all existing provider options or retry-policy settings. A paused source can become enabled by editing it. Source filters offer Active/Paused, but the main form has no corresponding status control. `Ready` is derived from enabled status, not a token/provider validation. Offer `errors` are hardcoded to zero; traffic-source errors are a dash.

**Improve:** Preserve settings explicitly, expose the relevant enable/pause control, and show configuration validity separately from enablement and delivery health. Define measurable error categories rather than displaying fabricated zeroes or ambiguous placeholders.

Sources: [source save payload](/D:/Track.in/src/app/admin/traffic-sources/traffic-source-form.tsx:128), [source status display](/D:/Track.in/src/app/admin/traffic-sources/traffic-sources-table.tsx:61), [offer error field](/D:/Track.in/src/app/api/admin/offers/route.ts:21).

### A26 · P2 · Delivery diagnostics and retry configuration are incomplete

### A32 · P2 · Database invariants and change history need strengthening

Ownership is checked in application code but is not enforced across related account-owned rows using composite database relationships. No current cross-owner campaign links were found, but a future unchecked write could create them. ## Release gates and recommended order

### Gate 1: attribution and outbound reporting

Resolve A01-A04, A11, A13, and the reporting-relevant parts of A15-A17/A22. A controlled test must show a new platform click ID becoming one correct visit, the expected event(s), one durable delivery per intended event, and platform confirmation. Cover custom external parameter names and repeated deposit transaction IDs. Prove reload/navigation does not create unwanted visits and a fresh ad arrival cannot inherit another campaign's attribution.

Include normal/incognito browsers, storage denied, the affected RDP browser, and both local and remote network locations. Browser timezone emulation tests reporting logic; it does not replace a real geographic/network reachability test. No timezone-based rejection was found in click intake. The old RDP failure remains unproven until a network trace or matching request log shows which stage failed.

### Gate 2: account security and commercial access

Resolve A06-A08, A10, A20, and A23. Verify two-account isolation through both UI and API, including identical external event IDs. Test paid, unpaid, expired, canceled, suspended, and lifetime accounts. Verify outbound destination restrictions and secret handling. Finish account recovery before accepting paid customers who can otherwise lock themselves out.

### Gate 3: real billing

Resolve A05/A09/A31. Demonstrate one real or provider-sandbox payment activating exactly the intended plan, duplicate/out-of-order webhooks not granting extra access, correct amount/network/asset checks, persisted invoice history, renewal, expiry, cancellation, and failed-payment recovery. Stop presenting a decorative pattern as a usable payment QR.

### Gate 4: release and operations

Resolve A12/A18/A19 and operational parts of A26/A32/A33. Require green tests that actually run, compatible migrations, post-deploy database/worker checks, crash recovery, rollback, backups, and a completed restore rehearsal. Test representative traffic volume before publishing capacity promises.

### Gate 5: customer workflow and consistency

Resolve A14/A21/A24-A30. Make setup/editing truthful and consistent, add the missing inspection/pagination paths, remove misleading labels, and complete keyboard/mobile checks on authenticated pages. Use a small, controlled customer pilot before a general launch, with reconciliation of platform counts and a documented support response process.
